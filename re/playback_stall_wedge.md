# Playback URB stall with no recovery path ("the wedge")

Log of every observed occurrence of a playback URB stream that stalls and
never recovers on its own. Distinct from the rate-change capture stall
documented in `rate_change_stall.md` (resolved 2026-08-17, cause identified
and fixed): this one hits **playback**, is not triggered by a rate change,
and the driver has no self-healing path for it at all — see the "gap" section
below. Kept separate per project memory (`jockey3-open-findings`, finding #3):
"It belongs with the existing open findings on device wedging, not folded
into the capture-stall mitigations that already handle the ordinary case."

Two occurrences of the silent stall so far, plus a third failure that showed
up 2026-08-19 under a different signature entirely -- see "Two failure
signatures" below. Too few of either to draw conclusions about trigger or
frequency; this file exists so the next occurrence, of either kind, has
something to compare against instead of starting from scratch.

## Two failure signatures (plus a third the driver cannot see)

Not one failure mode -- two that the kernel log shows and the run log's
Failure column distinguishes, plus a third that leaves no trace there at
all:

- **stall**: URBs silently stop completing. The card stays enumerated, EP0
  may or may not still answer, and nothing recovers on its own -- this is
  "the wedge" this document is named for; see "The gap" below for why the
  driver has no path out of it. Both 2026-08-11 and 2026-08-18 were this.
- **disconnect**: `-71` (EPROTO) URB errors cascade across all three
  endpoints within milliseconds of each other, the device drops off the USB
  bus (`USB disconnect`), and it then re-enumerates on its own a few seconds
  later -- self-recovering, at the cost of the driver reloading against a
  fresh device. First seen 2026-08-19, see the occurrence below. Whether
  this and the silent stall share a root cause (the same USB-facing MCU
  failing under load, just manifesting two different ways depending on
  exactly where in its own processing it gets stuck) or are two unrelated
  bugs is open.
- **control-surface freeze** (not in the table -- see "A third symptom..."
  under the third occurrence below): the Hot Cue LEDs stop responding to
  blink messages while the driver reports a completely clean run --
  zero URB stalls, zero write failures, zero unexpected dmesg lines. Only
  caught because a person was watching the device; the run log has no way
  to detect this at all with current instrumentation.

## The gap

`jockey3_pcm_prepare()` checks capture liveness only
(`needs_recovery = substream->stream == SNDRV_PCM_STREAM_CAPTURE && !alive(&chip->capture)`)
and calls `jockey3_recover_capture_stream()` (URB restart → full USB reset →
give up) when it finds a dead ring. Playback has no equivalent: nothing ever
asks whether the playback ring is alive before or during use. Since MIDI OUT
rides in byte 480 of every playback packet and the playback URBs run for the
device's whole lifetime rather than around PCM open/close (see `jockey3.c`
`DOC:` blocks), a dead playback ring means MIDI OUT is silently gone until
something outside the driver (a full disconnect/replug, or opening capture
which happens to reset the whole device) clears it.

`jockey3_watchdog_work()` *detects* the stall (that machinery is solid — see
the heartbeat-capping fix below) but is deliberately detection-only; the
comment on it says outright that "a stall that survives this long means
nothing is dealing with it" for exactly this case.

Mitigation sketched in project memory, not yet implemented: extend
`jockey3_pcm_prepare()`'s `needs_recovery` check to be direction-agnostic so
a playback open can also discover and recover a dead ring. Two caveats noted
there: don't copy `jockey3_recover_capture_stream()` verbatim (it is
capture-specific in name, logging and escalation — needs a direction-agnostic
version); and the 1 ms liveness rule cannot be applied to MIDI IN (bulk EP
`0x83` only completes when the device sends something, so idle MIDI IN would
look like a false stall).

## Occurrences

### 2026-08-11 — first occurrence, x86_64, found by hand

GitHub issue #26. Found during manual `JT-MIDI-001`/`JT-MIDI-002` runs, not
under the automated harness (which didn't cover this yet). Full writeup in
project memory `jockey3-open-findings` finding #3; summary:

- All three endpoints (playback `0x05`, capture `0x86`, MIDI IN `0x83`) died
  together — every `usb_submit_urb()` returned `-2` (`ENOENT`), i.e.
  `usb_pipe_endpoint()` found no endpoint there while the driver still
  believed it was bound. EP0 control transfers timed out with `-110`.
- Earliest symptom: `rawmidi drain error (avail = 4090, buffer_size = 4096)`
  repeating every ~10.5s — 6 bytes short (one LED message), 10s being ALSA's
  drain timeout.
- Playback `open → hw_params → prepare → trigger → close` logged nothing
  wrong while `aplay` got `-EIO`. Only capture *open* detected the stall,
  restarted URBs, and — because the ladder escalated — forced a full USB
  reset that happened to fix everything, incidentally, for a direction
  nothing in that codepath was trying to fix.
- Rate changes did not help; they failed at EP0 first, consistent with the
  whole device being wedged rather than just the audio rings.
- Cause of entry unknown; appeared during/after a `JT-MIDI-001` run followed
  by `JT-MIDI-002`. Trigger not isolated — sustained MIDI traffic was present
  but not proven causal.

### 2026-08-18 — second occurrence, arm64 (pi4test), automated (`JT-MIDI-007`)

`arm64-prod/20260818T215659Z-functional`, first time reproduced under the
automated harness. `JT-MIDI-007` runs 1800s of sustained MIDI traffic at
`load_fraction=0.9`, 8 messages/burst — i.e. it floods MIDI OUT continuously,
which rides in the playback stream. Result: `outcome: fail`.

- Playback URB stream stalled at `urb_stall_onset_ms` 908ms into a completion
  gap, **~1573s into the case itself** (~87% through the 1800s window,
  `9994.247478 - 8420.996487` from the kernel log's own timestamps against
  this case's `JT-MARK`) — and **never recovered** for the remaining ~230s of
  the test. Capture stalled at the same moment (`urb_stall_onset_ms` 1019ms)
  but that side is the expected/deferred idle-capture case, not part of this
  finding. See the run log above for how this was recomputed; an earlier
  version of this section had the onset at "~9994s wall-clock", which was the
  kernel's raw uptime timestamp, not time-into-the-case.
- Heartbeats at +61s/+122s/+182s after onset all still read "stalled".
  `rawmidi drain error` repeated every ~10s (ALSA's drain timeout) right up
  to the end of the run — MIDI OUT was dead for the rest of the test.
- `urb_stalls_playback: 1`, `urb_stalls_capture: 1`, `write_failures: 0` (the
  writer itself never saw an error — the loss was silent from userspace's
  point of view apart from the drain timeout). `achieved_bps: 1397.3`
  against a nominal 2812 B/s target — see "Test-harness rate-pacing bug"
  below; this run was not actually driving the rate it was configured for.
- Unlike 2026-08-11, MIDI IN and EP0 were not confirmed dead — this run only
  exercises playback (MIDI OUT) and capture, so whether the whole device
  wedged the same way as issue #26 or only the playback ring died this time
  is unknown; would need an EP0 probe (e.g. a rate query) during the stall to
  tell them apart. Not attempted, since the finding was in dmesg after the
  fact, not caught live.
- **Caveat:** the driver under test was dirty (`git_describe: 8e05d2a-dirty`,
  `kernel_driver_dirty: true`, built on `alsa-dev` from `~/sound-build`).
  Not a clean-commit reproduction. Worth re-running once the tree is clean.

### 2026-08-19 — repeat on arm64 (pi4test), did not reproduce

`arm64-prod/20260819T154422Z-functional`, same case, same params
(`load_fraction=0.9`, 8 messages/burst, 1800s), against a **clean** driver
commit (`28f112c`, `kernel_driver_dirty: false`) this time. `outcome: pass`,
`urb_stalls_playback: 0`, `urb_stalls_capture: 0`. Does not confirm or rule
out anything on its own — one clean run against one dirty-tree wedge is not
enough to call the dirty tree causal, and both runs were throttled to well
under their nominal target rate anyway (see below), so neither has really
tested the MIDI-rate hypothesis yet.

### 2026-08-19 — third occurrence, arm64 (pi4test), automated (`JT-MIDI-007`) — new signature: disconnect

`arm64-prod/20260819T174034Z-functional`, first run under the fixed harness
(see "Test-harness rate-pacing bug" below) to actually approach the intended
rate: `achieved_bps: 2479.2` against a 2812 B/s target (88%, versus ~50-57%
for every earlier run). `outcome: fail`, `duration_s: 281` against a planned
1800s.

- No "URB stream stalled: no completion" line anywhere in this run — this is
  not the same signature as 2026-08-18. Instead, `-71` (`EPROTO`) errors hit
  all three endpoints (playback, capture, MIDI IN) within about 5ms of each
  other, 8 consecutive errors per endpoint, then a real USB disconnect:

  ```
  Playback URB error: -71 (1 consecutive) ... (8 consecutive)
  MIDI IN URB error: -71 (1 consecutive) ... (8 consecutive)
  Capture URB error: -71 (1 consecutive) ... (4 consecutive)
  Playback stopped after 8 consecutive URB errors; deferring recovery
  MIDI IN stopped after 8 consecutive URB errors
  Capture stopped after 8 consecutive URB errors; deferring recovery
  usb 1-1.1: USB disconnect, device number 3
  usb 1-1.1.1: USB disconnect, device number 31
  ```

- Onset ~248s into the case (~14% through the 1800s window), at 676,224
  bytes sent — far earlier than the 2026-08-18 stall's ~1573s/~2.51 MB, and
  at a much higher achieved rate. Consistent with (not proof of) rate being
  a real factor: higher load, faster failure.
- **Self-recovering, unlike the silent stall**: the device re-enumerates on
  its own a few seconds after disconnecting. Confirmed live — a follow-up
  `JT-MIDI-007` run started automatically afterward and hit the *same*
  `-71`-cascade-then-disconnect pattern again within its own window
  (`jockey3_urb_error_give_up: 6 callbacks suppressed` on the next
  occurrence, meaning it had already repeated several times in a short
  span). This looks readily reproducible at the higher achieved rate, in
  sharp contrast to the two earlier silent-stall occurrences (one manual,
  one automated, months apart).
- `driver_commit: 28f112c` (clean, `kernel_driver_dirty: false`) — same
  clean commit as the 2026-08-19 repeat that did *not* fail, and firmware
  `1.0.6`, same as every run so far. The only material difference from the
  repeat that didn't fail is the achieved rate (1604 B/s vs 2479 B/s).
- Frank separately observed the Hot Cue LED pattern (the same LEDs
  `JT-MIDI-007` toggles) freeze mid-run on **both** the x86_64 and arm64
  machines around t≈500s (±50s) during a later pair of runs, resuming on
  the x86_64 side around t≈700s. That is a third distinct symptom timeline
  worth tracking once those runs finish and their dmesg/run.json can be read
  — a temporary freeze-then-self-recover, neither a full disconnect nor the
  permanent silent stall, would be a third data point on how this device
  fails under load rather than a third bug.
- **Firmware is not uniform across the two Remix units.** Confirmed by
  `env.firmware.version` in each machine's own run.json: the x86_64-prod
  unit is **firmware 1.0.3**, the arm64-prod (pi4test) unit is **1.0.6**.
  Frank reports the freeze/resume/freeze pattern on the 1.0.3 (x86_64) unit
  looks repetitive -- stop, resume, stop again -- rather than a single
  freeze-then-recover; more precise timing pending, see the next point.
- **A third symptom exists that this table cannot detect at all, and it is
  now the most reliably reproducible one of the three: confirmed across two
  independent cycles, 2-for-2 on each unit.** Four runs so far, all at
  ~99.9% of the target rate (the closest any runs have gotten, now that the
  harness fix actually lets a run reach it) and all `outcome: pass` with a
  completely clean driver-level record -- zero URB stalls, zero write
  failures, zero unexpected dmesg lines, full planned duration completed:

  - `x86_64-prod/20260819T174412Z-smoke` and
    `x86_64-prod/20260819T181715Z-smoke` (firmware **1.0.3**): LEDs
    periodically stopped responding to the blink messages both times,
    described as repetitive -- stop, resume, stop again.
  - `arm64-prod/20260819T174543Z-functional` (the run that started
    automatically right after the disconnect occurrence above) and
    `arm64-prod/20260819T181708Z-functional` (firmware **1.0.6**): LEDs
    froze both times and, unlike the x86_64/1.0.3 unit, did **not** recover
    on their own for the rest of the run.

  Same symptom on both physical units, both firmware revisions, both at the
  highest achieved rate seen so far, with the *same* recovery-behavior split
  by firmware repeating on the second cycle -- 1.0.3 repetitive, 1.0.6
  permanent-until-external-intervention. That is no longer a one-off
  observation; it looks like a firmware-version-dependent difference in how
  this fault behaves once triggered, not just whether it triggers. In every
  case the driver reports nothing wrong at any level: every byte the case
  thinks it sent was accepted without error. Whatever is dropping the LED
  updates is happening downstream of what the driver or this table can see
  at all -- consistent with Frank's earlier schematic-based theory that the
  isolated UART link between the USB-facing "Ploytec" MCU and the Control
  Surface MCU (STM8S207) is where data gets lost, independent of whether
  the USB side (what `stall`/`disconnect` above actually detect) is
  healthy. Whether this, the silent stall, and the USB disconnect are three
  faces of the same root cause or genuinely separate bugs is still open,
  but the fact this one reproduces reliably at the highest achieved rate on
  both units, while the two USB-level signatures have one occurrence each
  so far, makes it the most promising one to characterize precisely next.
  No automated detection
  exists for it yet; it takes a person watching the device.

### Test-harness rate-pacing bug, found and fixed 2026-08-19

While looking at why the 2026-08-19 repeat's `achieved_bps` (1604.4) was so
far under its `load_fraction`-scaled target (2812), found that
`run_burst_window()` — the loop behind `JT-MIDI-007`'s endurance mode — was
still spawning an `amidi` subprocess per burst. That is exactly the
process-spawn overhead already diagnosed and fixed for `JT-MIDI-004`'s
per-rate mode on 2026-08-16 (a constant ~59%-of-target readback regardless
of the configured rate, the signature of per-call spawn cost rather than a
real rate effect) — it had just never been applied to the endurance mode
too. 1604/2812 = 57.0% and 1397/2812 = 49.7% (the original wedge run) are
both consistent with that same signature.

Fixed in `cases/midi.py` (`run_burst_window()` now opens the rawmidi device
node once and `os.write()`s each burst directly, like `JT-MIDI-004`'s
`measure_throughput()` already did) and verified on pi4test: a 60s run now
achieves 2807.8/2812 B/s (99.8%), see the run log's fourth row. Committed
`855098f` in `alsa-jockey3`.

**This means every `JT-MIDI-007` run to date, including both stall
occurrences, ran at roughly half its intended MIDI OUT rate.** The
MIDI-rate-trigger hypothesis has not actually been tested at the rate the
case was configured to drive. A fresh round of runs under the fixed harness
is needed before any conclusion about rate as a factor means anything.

### Working hypothesis, unproven

Both occurrences happened during sustained/heavy MIDI OUT traffic (manual
flood-testing in 2026-08-11, `JT-MIDI-007`'s scripted flood in 2026-08-18).
Whether the wedge needs MIDI-OUT load specifically, or just needs the device
running long enough and MIDI happens to be what these two sessions were
exercising, is open. The next data point worth having: does the same wedge
ever show up in a long run with **no** MIDI traffic and an undisturbed
playback ring. `JT-RATE-001` does not qualify for this — a rate change tears
down and restarts the URBs (see `jockey3.c` `DOC:` blocks), so it can't
distinguish "URBs kept running the whole time and never stalled" from "the
ring got torn down and rebuilt before it had the chance to." `JT-PCM-008`
(sustained duplex, formerly `JT-SOAK-001`) is the right candidate: pure
audio, no MIDI, no rate changes, URBs run continuously for the whole soak.

An 8-hour `JT-PCM-008` control run on arm64 (`20260819T032404Z-functional`,
see the run log above) completed clean with no wedge — consistent with (not
yet proof of) MIDI-OUT load being required to trigger it, since a MIDI-free
run 4x longer than any `JT-MIDI-007` attempt so far never wedged.

The first run under the fixed harness to reach a high achieved rate
(88% of target, `20260819T174034Z-functional`) failed in ~248s — the
fastest failure of any run so far, and apparently readily reproducible at
that rate (see the third occurrence above). Every prior run, at ~50-57% of
target, either never failed or took ~1573s to. That is consistent with rate
being a real factor, though it is the *disconnect* signature this shows up
in, not (yet) a repeat of the silent stall — so this is evidence about "does
MIDI-OUT load provoke a device failure", not yet evidence about which of the
two signatures a higher rate makes more likely, or whether they are the same
underlying bug wearing two faces.

Next: sweep the rate (now that the harness can actually hit it) around the
~3125 B/s / 31250 bps boundary Frank separately observed the control-surface
LEDs degrading at, watching for both signatures, not just the original
silent stall.

**Rate sweep, first point — `load_fraction=0.4` (~1250 B/s), 2026-08-19:**
one run per unit (`arm64-prod/20260819T185534Z-functional`,
`x86_64-prod/20260819T185622Z-smoke`), both 1800s, both clean at the driver
level (as every run has been) *and* clean on the control surface this time —
LEDs kept blinking consistently on both units for the full run, no
stop/restart on 1.0.3, no freeze on 1.0.6. First negative result after four
consecutive positive ones at ~2810 B/s (99.9% of the 0.9 target). Consistent
with a real rate threshold somewhere between ~1250 B/s and ~2810 B/s, not
just "run long enough and it happens eventually" — though one run per unit
at the low end is a thinner base than the four at the high end.

**Rate sweep, second point — `load_fraction=0.7` (~2188 B/s), 2026-08-19:**
one run per unit again (`arm64-prod/20260819T193020Z-functional`,
`x86_64-prod/20260819T193028Z-smoke`), both 1800s, both clean throughout --
driver and LEDs both, on both units. Narrows the threshold (if there is a
clean one) to somewhere in (2188, 2810] B/s.

**Rate sweep, third point — `load_fraction=0.8` (~2500 B/s), 2026-08-19:**
one run per unit again (`arm64-prod/20260819T200200Z-functional`,
`x86_64-prod/20260819T200209Z-smoke`), both 1800s, both clean throughout,
same as 0.4 and 0.7. Narrows the threshold further to (2500, 2810] B/s --
a fairly tight band now, ~11% of the ceiling.

**Rate sweep, fourth point — `load_fraction=0.85` (~2660 B/s), 2026-08-19,
in progress:** unlike 0.4/0.7/0.8, not clean. After ~7 minutes of stable
running, Frank observed **occasional very short (1-2s) LED stalls** on both
units -- a fourth texture, distinct from all three seen so far: not a single
permanent freeze (arm64/1.0.6 at 0.9), not continuous stop/restart
(x86_64/1.0.3 at 0.9), and not clean (everything at ≤0.8). Consistent with
0.85 sitting right at or just past the real threshold, where the fault
starts but doesn't yet manifest every time -- exactly what a boundary region
should look like. No URB stalls reported at any rate tested so far in this
whole sweep, for what that is worth: the USB streaming layer itself looks
solid throughout: whatever is happening lives downstream of it, at every
rate tried.

### Mitigation implemented: lowered the leaky-bucket ceiling, 2026-08-19

With the sweep converged -- (2500, 2810] bracketing the fault, 0.85 showing
intermittent short stalls right at that edge rather than a clean pass or a
hard failure -- and given a normal DJ-controller workload never needs
anywhere near this ceiling (the Windows driver runs MIDI OUT at only
355 B/s, and this device's entire addressable surface -- 46 LEDs, rings and
VU-bars -- is ~138 bytes to update all at once), Frank decided to lower the
driver's leaky-bucket limiter from ~3125 B/s (approximating the raw 31250
bps MIDI line rate) to a deliberately conservative 2500 B/s -- below the
observed edge, not just under it, since the edge itself was measured on two
specific units and shouldn't be treated as a hard boundary for hardware in
general. At 2500 B/s the device still supports well over 18 full-panel
updates/sec, far beyond what's perceptible or needed.

Changed in `jockey3_get_next_midi_out_byte()` (`jockey3.c`) and mirrored in
`cases/midi.py`'s `CEILING_BPS` (kept the historical measurement notes in
that file's docstring as-is; they were correct for the old constant and are
not rewritten). `re/wedge_run_log.py`'s own `CEILING_BPS` was deliberately
**not** changed -- every row logged so far was run against the old ~3125
constant, and bumping it would silently recompute their "Target rate" cells
against a ceiling those runs never used; see the comment there for what to
do if the ceiling changes again. Verified: out-of-tree `make` clean,
`checkpatch.pl --strict --codespell --no-tree --file jockey3.c` clean (only
the two pre-existing CamelCase CHECKs on unrelated lines), `kernel-doc
-Wall -Werror --none jockey3.c` clean, `tests/hw/selftest.py` 209/209.

Not yet validated on hardware against the new ceiling -- the whole sweep
above was run to find the right number, not to confirm the driver enforces
it correctly once changed. A follow-up `JT-MIDI-004` run (asserts
`achieved_bps` against `CEILING_BPS`) once this is built and loaded would
close that loop.

## Heartbeat spam, fixed 2026-08-18

Not the wedge itself, but found while reading this run's dmesg: on an
otherwise idle pi4test with no wedge at all — just the ordinary
deferred-idle-capture case (`jockey3_pcm_hw_params()`'s designed behavior,
not a fault) — `jockey3_watchdog_work()`'s "still stalled" heartbeat repeated
every 60s indefinitely, for the entire uptime of the device. Flagged as a
mainline-submission blocker: unconditional log spam for a state the driver
itself considers benign is exactly what LKML review rejects.

Fixed by capping heartbeats per stall to `JOCKEY3_WATCHDOG_HEARTBEAT_MAX` (3)
in `jockey3_watchdog_check()`/`struct jockey3_pcm_urb_stream::stall_heartbeats`
(`jockey3.c`). After the third reminder the message says so
("; no further reports until it clears") and goes silent until the stream
either recovers (still logs a recovery line whenever that happens, no matter
how much later) or a fresh onset resets the counter. Applies to both the
idle-deferred-capture heartbeat and the "everything else" (this file's wedge)
heartbeat — a real, undealt-with wedge is exactly as capable of running for
days as the benign deferred case is, so it needs the same cap.
